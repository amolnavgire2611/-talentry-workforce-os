## Confirmed implementation issues and risks

1. **Resolved in this implementation slice:** removed the duplicate `GET /api/employees/me` handler and added an OpenAPI operation-ID uniqueness assertion.
2. **Resolved in this implementation slice:** employee updates no longer query or modify leave balances. An isolated regression test verifies an employee profile edit succeeds and preserves the associated leave allocation and used days. Leave allowances remain managed by leave-policy workflows.
3. Public Employee registration creates a User without an Employee link, while the Employee page requires a linked Employee row and returns 404 otherwise. A reviewed profile-linking/onboarding flow is required.
4. Invitation registration is implemented; the prior `/api/auth/activate` endpoint remains as a hidden compatibility alias. Email delivery is not implemented, so administrators must deliver registration codes through a trusted private channel. Expired codes can be rotated from the Access & users page.
5. Root `FEATURE_MATRIX.md`, `PROJECT_PLAN.md`, and `SECURITY_REVIEW.md` retain old claims for historical context and link to `docs/` as the authoritative current baseline; do not use their old status rows as release evidence.
6. `backend/application.py` includes multiple domains, permissions, rate limiting and workflows in one module. Process-local IP throttling does not protect a multi-worker deployment.
7. **Updated:** JWT verification checks signature, algorithm, type, subject, expiry, issuer and audience. Refresh-session rotation and revocation are implemented. Password reset/MFA are still absent, and login throttling remains process-local.
8. **Partially resolved:** Organization and non-null organization foreign keys now exist, legacy records map to NEXORA, ORM reads and bulk writes are tenant-scoped, and cross-org API isolation is tested. Organization membership and multi-organization onboarding, target role permissions, composite tenant-aware relationship constraints, raw SQL review, and PostgreSQL verification remain open; do not treat this as full multi-tenant readiness.
9. Config has a development signing key fallback; production checks reject it, but startup validation should also cover production database, CORS, cookie/HTTPS settings and bootstrap key lifecycle.
10. UI roles Recruiter/Payroll Administrator have overview/settings navigation but no respective business modules; the dashboard must remain explicit about unavailable modules.

## Dependency/configuration assessment

- Frontend exact resolved installs are represented by `package-lock.json`; `package.json` uses compatible semver ranges. Vitest and React Testing Library cover API helpers and auth components; Playwright remains absent.
- Backend `requirements.txt` pins every listed dependency but includes no PostgreSQL driver, Python lint/type-check tooling, test-client browser stack or production server image. Backend lint/type checks therefore are not yet a verified gate; add and configure them during the operations/tooling stage.
- CORS defaults to local Vite origins. `APP_ENV`, signing secret, access-token lifetime, directory toggle and bootstrap-key configuration are environment-based. No Docker, CI, email, object storage, monitoring, or secrets-manager integration is present.
- Core requirements should remain runnable without paid APIs; email, object storage scanner and other integrations require optional local/development adapters and clear delivery state.
